**Due:** Sprint 4
**Focus:** Visual System Design Artifacts

## Overview

Effective software development requires clear, shared understanding of what you're building. This checkpoint requires you to create visual design artifacts that communicate your system's structure, behavior, or user experience. These artifacts bridge the gap between abstract product strategy and concrete implementation, helping your team, client, and future maintainers understand your technical and design decisions.
Design artifacts serve multiple purposes: they guide current development work, facilitate team coordination, communicate with stakeholders, and document decisions for future teams.

## Context

"Design" here means the technical and interaction architecture of your system - how components relate, how users interact with features, how data flows through the system, or how the interface is structured. This is design in the software engineering and product planning sense, not graphic design or branding.
The specific artifacts you create should match your project's current needs. Different projects at different stages need different types of design artifacts.

## Requirements

Create visual design artifact(s) appropriate to your project. Choose from:

## System Architecture

- Component diagrams showing major system parts and their relationships
- Deployment architecture showing how your system is hosted and scaled
- Service interaction diagrams for distributed systems
- Database schema diagrams

## Software Architecture

- Class diagrams or module relationships
- Data flow diagrams showing how information moves through your system
- State diagrams for complex workflows or processes
- API architecture and endpoint relationships

## User Experience and Interaction Design

- Wireframes of key screens or workflows
- User flow diagrams showing paths through your application
- Information architecture diagrams
- Interaction patterns for key features

## Data and Information Design

- Data model diagrams
- Information flow diagrams
- Entity relationship diagrams
- Data transformation pipelines

## Your artifacts should:

## For existing products:

- Document the current state of the system accurately
- Identify intended future state where it differs from current reality
- Highlight areas of technical debt or planned refactoring

## For new products:

- Communicate the intended system design clearly
- Provide enough detail to guide implementation decisions
- Show key architectural or interaction design decisions

## All artifacts should:

- Be primarily visual (diagrams, wireframes, flowcharts, etc.)
- Include minimal necessary text labels and annotations
- Use standard notation when applicable (UML, flowchart symbols, etc.)
- Be clear enough that someone unfamiliar with your codebase can understand your system

## Deliverables

- Visual design artifact(s) (PDF or link to design files in your repository)
- Brief context document (1 page max) explaining:
- What artifacts you created and why you chose these specific types
- Key decisions or trade-offs the artifacts illustrate
- How these artifacts inform current or future development work
- For existing products: What differs between current and intended state
- Add a link to original documents for anything created with online tools.

## Evaluation Criteria

## Appropriateness

- Artifacts match your project's actual needs
- Type of design artifact makes sense for your product and stage
- Level of detail is appropriate for your purpose

## Clarity

- Visual artifacts communicate clearly
- Someone unfamiliar with your product can understand your system
- Key relationships and structures are evident
- Standard notation used correctly (when applicable)

## Utility

- Artifacts serve genuine purpose for your team or stakeholders
- Artifacts inform actual development decisions
- Documentation is useful for future maintainers

## Completeness

- Artifacts show sufficient detail to be actionable
- Key system components or user flows are represented
- Context document explains what's shown and why it matters

## Notes

- **Match your needs:** Don't create artifacts just to check boxes - create what your team actually needs
- **Visual primacy:** Diagrams and wireframes communicate faster than text
- **Tool flexibility:** Use whatever tools work for you (draw.io, Figma, PenPot, Miro, whiteboard photos, etc.)
- **Standard notation helps:** UML, flowchart symbols, and common patterns make artifacts easier to understand
- **Living documents:** These artifacts should evolve as your system evolves
- **Accessibility:** If visual artifacts aren't accessible for your team, include text descriptions or alternative formats
- **Different projects need different things:** A new mobile app needs wireframes; a data pipeline needs flow diagrams; a refactoring project needs before/after architecture diagrams, etc.
